# Система инцидентов

## Зачем она появилась

В августе 2026 обнаружилось, что сервис-аккаунт потерял права **Редактора**
на таблицу `vnxSHOP`. Последствия:

- чтение работало → каталог грузился → бот выглядел абсолютно здоровым;
- запись падала с `403` → прайсы поставщиков не попадали в таблицу;
- публикация в канал шла из памяти → в канале всё выглядело свежим;
- фид Meta Commerce Manager замер на старых ценах.

Ошибка при этом честно писалась в `logger.error` — и умирала в journalctl,
потому что в логи никто не смотрит, пока что-то заметно не сломается.

Вывод, из которого выросла система: **опасна не ошибка, а ошибка, которую
никто не увидел**. Хуже всего поломки, при которых система продолжает
рапортовать об успехе.

## Из чего состоит

| Файл | Роль |
|---|---|
| `services/incident_rules.py` | Каталог известных поломок: код, серьёзность, причина, инструкция по починке |
| `services/incidents.py` | Движок: регистрация, дедупликация, хранение, уведомления |
| `services/watchdog.py` | Активные проверки: при старте и раз в час |
| `handlers/incidents.py` | Команды владельца в Telegram |
| `data/incidents.jsonl` | История, переживающая перезапуск |

## Уровни серьёзности

| | Уровень | Смысл | Уведомление |
|---|---|---|---|
| 🔴 | `critical` | Бизнес-процесс встал, товар и деньги не двигаются | Всегда, шторм-лимит не действует |
| 🟠 | `error` | Операция провалилась, система работает частично | Да |
| 🟡 | `warning` | Аномалия, сама по себе не ломает | Да, с ограничением частоты |
| 🔵 | `info` | Событие для истории | Нет, копится молча |

## Команды в Telegram

Доступны только владельцу (`MANAGER_ID`).

```
/health              светофор: всё работает / замечания / поломки
/incidents           список открытых инцидентов
/incidents all       вместе с историей закрытых
/incident КОД        подробная карточка: почему важно и что делать
/incident            список всех известных кодов
```

### Тихие отказы

Инциденты, которые не рождаются из исключений. Их поднимает код, когда
результат формально успешен, но по сути неверен. Именно они живут дольше всего.

| Код | Уровень | Когда |
|---|---|---|
| `SYNC_WROTE_NOTHING` | 🔴 | Прайс разобран, а записано 0 строк. **Ловит ту самую поломку с правами** |
| `CATALOG_EMPTY` | 🔴 | Каталог в памяти пуст |
| `CATALOG_STALE` | 🟡 | Больше 24 ч без единого прайса от поставщиков |
| `PARSE_EMPTY` | 🟡 | Сообщение похоже на прайс, но разобрано в 0 позиций |
| `PUBLISH_FAILED` | 🟠 | Ни одно сообщение не ушло в канал |
| `PUBLISH_NOTHING_TO_SHOW` | 🟠 | Фильтр «только Apple» отсеял весь каталог |

## Как это работает

### Дедупликация

Повторы одной проблемы **не создают новых записей**. Растёт `count`,
обновляется `last_seen`. Отпечаток инцидента:

```
код | компонент | key
```

`key` нужен, когда однотипные сбои надо вести раздельно — например,
`PARSE_EMPTY` по каждому поставщику отдельно.

### Частота уведомлений

- первое появление — уведомление сразу;
- повторы — не чаще раза в `INCIDENTS_REPEAT_MINUTES` (по умолчанию 60);
- шторм — не больше `INCIDENTS_BURST_LIMIT` (12) уведомлений за 10 минут;
  `critical` проходит всегда.

### Самозакрытие

Успешная операция гасит инцидент через `incidents.ok(...)` или `resolve(...)`.
Уведомление «Восстановлено» уходит **только если об открытии успели сообщить** —
иначе владелец получал бы отчёты о починке проблем, о которых не знал.

### Работа из синхронного кода

`sheets_writer` синхронный, aiogram асинхронный. Поэтому `report()` только
кладёт уведомление в очередь, а разбирает её корутина `incidents.dispatcher()`,
запущенная из `main.py`. Синхронный код сообщает об инциденте, ничего не зная
про event loop.

`report()` **не бросает исключений вообще**. Система наблюдения, роняющая
наблюдаемое, хуже её отсутствия.

## Сторож

`services/watchdog.py` ловит поломки, которые не порождают ошибок.

**При старте** (через минуту после запуска) — проверяет переменные окружения
и проходит полную цепочку доступа к таблице: авторизация → открытие →
чтение → **запись**.

Проверять только чтение бессмысленно: при правах «Читатель» чтение проходит,
и бот выглядит здоровым. Проба записи неразрушающая — читаем `A1` и пишем
в неё то же значение.

> Пробовать запись в заведомо далёкую ячейку (вроде `ZZ1`) нельзя: Google
> ответит `400 exceeds grid limits` ещё до проверки прав, и это легко принять
> за отказ в доступе. На этом сломалась первая версия диагностики.

**Раз в час** — конфигурация, свежесть каталога, доступ к таблице.

## Настройки

Все необязательные, в `.env`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `INCIDENTS_FILE` | `data/incidents.jsonl` | Файл истории |
| `INCIDENTS_HISTORY_LIMIT` | `500` | Сколько записей хранить |
| `INCIDENTS_REPEAT_MINUTES` | `60` | Пауза между напоминаниями |
| `INCIDENTS_BURST_LIMIT` | `12` | Потолок уведомлений за 10 минут |
| `WATCHDOG_INTERVAL_MINUTES` | `60` | Период обхода |
| `WATCHDOG_STALE_HOURS` | `24` | Через сколько молчания каталог протух |

## Как добавить новый код

1. Опиши правило в `services/incident_rules.py`:

```python
_rule(
    code="MY_CODE",
    severity=ERROR,
    title="Что сломалось, одной строкой",
    why="Почему это важно и чем грозит",
    fix="Что конкретно сделать руками, чтобы починить",
)
```

2. Если код определяется по исключению — добавь `_Matcher` в `_MATCHERS`.
   Порядок важен: **первое совпадение выигрывает**, узкие правила выше общих.

3. Вызывай из кода:

```python
from services import incidents
from services import incident_rules as rules

incidents.report(component=rules.SHEETS, code="MY_CODE", detail="что делали")
incidents.resolve(rules.SHEETS, "MY_CODE")   # когда снова заработало
```

**Правило заведения кода:** если поломку нельзя починить конкретным
действием — не заводи для неё код, ей место в `UNKNOWN`. Код без внятного
поля `fix` бесполезен: он превращает алерт в шум.

## Диагностика с сервера

```bash
cd /opt/vnxChooseApple_bot && python run_sheets_check.py
```

Проходит ту же цепочку, что и сторож внутри бота — той же функцией
`check_access()`. Диагностика и бот не могут разойтись во мнениях
о том, работает доступ или нет.
